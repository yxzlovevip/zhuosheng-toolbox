# 更新占用与工具退出修复 v1.3.5

日期：2026-10-22。

## 问题证据

用户截图显示：1.3.3 更新到新版，在安装器替换目录时提示“另一个进程正在使用此文件，因此该进程无法访问此文件”，原版本保留。

用 1.3.4 成品安装器的实际 .NET Framework 安装引擎，在独立目录中继承旧 app 工作目录，复现了同样的 Directory.InternalMove 错误。Windows 会锁住进程的当前工作目录；更新安装器继承 app 工作目录后，旧版退出仍无法释放安装器自己的目录占用。

另外，原工具箱退出只对 Process 对象执行 Dispose，并没有结束工具。原有列表只记录直接启动的进程，漏掉启动器退出后继续运行的子进程。

## 修改

- 安装引擎发现自己的工作目录在旧 app 内时，先移到安装根目录，再替换目录，兼容旧客户端发起更新。
- 两个主界面的更新安装器都从 .updates 目录启动。
- 每个 ToolLauncher 使用独立、未命名、不可继承句柄的 Windows Job Object，启用 KILL_ON_JOB_CLOSE；通过 STARTUPINFOEX 的 PROC_THREAD_ATTRIBUTE_JOB_LIST 在创建工具的同时加入进程组，再恢复执行。避免工具抢先派生未跟踪子进程，也避免宿主恰好在创建与分配之间终止时遗留挂起进程。无法监管时阻止启动。
- 主界面关闭时结束整个进程组并等待退出；宿主异常终止时由 Windows 关闭句柄并结束进程组。保留另一个工具箱实例、更新安装器和外部浏览器的独立生命周期。
- 更新阻止条件检查进程组活动数量，包含原启动器已经退出的子进程。退出后也禁止仍在校验的启动请求重新打开工具。
- 启动提示与使用说明增加关闭工具箱时会结束工具的说明。

## 验证范围

测试工具只创建等待中的自身副本，不执行真实维护、清理、重装或驱动操作。覆盖正常退出、父进程先退出、宿主被直接终止、两个实例隔离、启动与退出并发，以及成品 .NET Framework 安装引擎的工作目录占用回归。

此管理约束适用于受管进程及其普通派生进程。第三方工具通过系统服务管理器、WMI 或外部代理创建的独立服务/进程，需要逐项审核，不能将 Job Object 测试当作所有第三方工具的真实安装、修复和服务生命周期验收。已完成的系统设置不会因结束工具自动恢复。
