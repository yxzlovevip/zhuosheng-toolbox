## 初次配置时的限制（历史）

现有交付目录是免安装运行版。`src/Toolbox.Setup`、正式安装 EXE 和安装升级流程尚未实现；客户端更新入口要求先安装到 `Program Files/InternalToolbox` 下的版本目录，并会向安装器传入 `--upgrade --wait-pid <主程序进程号>`。单独的 `CZToolbox.exe` 不能当作安装更新包发布。

目前没有线上 `latest.json`。该地址有意返回 HTTP 503 和 `Cache-Control: no-store`；客户端会显示“检查更新失败”，现有工具仍可使用。它不表示证书或网络故障，也不表示已有更新可下载。只有完成正式安装器及旧版升级验证后，才应发布签名清单。未更改客户端产品逻辑来掩盖这一缺口。

## 后续生成发布文件

使用 PowerShell 7 执行以下示例；`Installer` 必须指向经过安装、退出等待和升级验证的正式安装器。脚本只生成发布材料，不验证安装器行为，也不上传或切换线上版本。

```powershell
./scripts/New-UpdateRelease.ps1 -Installer '正式安装器的完整路径.exe' -Version '1.0.1' -Notes '本次更新说明'
```

输出为 `artifacts/update-releases/1.0.1/`，包含：

- `CZToolbox-1.0.1-setup.exe`。
- `SHA256SUMS`。
- `latest.json`：UTF-8 JSON 外层有 Base64 编码的 `payload`、`signature`，使用 RSA-SHA256/PKCS#1 v1.5；负载声明版本、同站 HTTPS 下载地址、大小、SHA-256、说明。

脚本会核对公私钥匹配和复制后的文件大小、哈希，拒绝覆盖现有输出目录。不要重新生成密钥替换现有客户端公钥。

## 正式发布顺序

1. 完成正式安装器及目标机器上的旧版升级测试。提高应用自身版本，保证构建版本与清单版本一致；当前版本在主项目、客户端服务和界面中仍有固定的 `1.0.0`。
2. 生成上述签名发布材料，上传到服务器新的 `releases/1.0.1/`；不覆盖已发布版本，不上传 `.private`。
3. 核对服务端和公网下载的大小、SHA-256、签名和版本内容，确认 EXE 地址直接返回 200，没有跳转。
4. 如果已有根清单，先复制到 `/var/backups/cz-updates/`；将新清单复制为更新根目录中的临时文件，再用同文件系统重命名原子替换根 `latest.json`。仅上传版本目录不会启用线上更新。
5. 用真实旧版客户端核验发现新版、下载验签、关闭工具、退出主程序、升级和重启。失败时把备份清单原子恢复，并保留安装失败日志。
